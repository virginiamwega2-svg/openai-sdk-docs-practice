# AI API Observability and Troubleshooting Guide

## 1. Overview: Why AI Observability Matters

### What Is AI Observability?

AI observability is the practice of collecting and analyzing information about an AI application's behavior to understand what happens during a request, identify failures, investigate performance issues, and evaluate response quality.

Traditional API monitoring often focuses on availability, response time, and errors. AI applications need additional visibility because a request can succeed technically while still producing an incorrect, irrelevant, or unhelpful answer.

### Why Does It Matter?

AI observability helps developers answer questions such as:

- **Performance:** Why is an AI request taking longer than expected?
- **Streaming:** Why has a streamed response stopped before completion?
- **Usage and cost:** How many tokens did a request consume, and what was its estimated cost?
- **Reliability:** Are requests failing because of timeouts, rate limits, or other API errors?
- **Answer quality:** Has a model or prompt change made responses less accurate or relevant?
- **Debugging:** Which stage of an AI workflow caused the problem?

Without sufficient observability, developers may see that an application is failing without having enough evidence to explain why.

### Example: Investigating a Slow AI Request

Imagine an application that uses an AI API to summarize documents. Users report that summaries sometimes take too long to appear.

Possible causes include:

1. The application takes too long to prepare the input.
2. The AI API takes too long to begin responding.
3. The model generates the response slowly.
4. The application processes or delivers the response inefficiently.

Measuring request duration, time to first token (TTFT), and generation time can help narrow down the cause. Traces can provide additional context about the stages involved.

These measurements provide evidence for an investigation; they do not automatically identify the root cause.

### Core Areas of AI Observability

AI observability commonly combines four complementary areas:

- **Metrics:** Numerical measurements such as request latency, error rate, token usage, and estimated cost.
- **Logs:** Recorded events and errors that help explain what happened during a request.
- **Traces:** A view of the stages a request passes through and the relationships between those operations.
- **Evaluations:** Checks of AI output quality, such as correctness, relevance, and consistency.

Together, these signals help developers investigate technical failures and quality regressions.

### Scope of This Guide

This guide explains practical observability concepts for AI API and SDK integrations, including performance measurements, traces and spans, streaming troubleshooting, evaluation, privacy, sampling, and retention.

It distinguishes between recommended practices and capabilities actually implemented or verified in the accompanying project. Describing an observability technique does not mean that the project already implements it.

## 2. What to Measure: Latency, TTFT, Tokens, Errors, and Cost

### Latency

Latency is the time taken for a request to complete. For a streaming AI response, total latency can be measured from when the request is sent until the response finishes.

Latency helps developers investigate slow requests and understand how an application's performance changes over time.

### Time to First Token (TTFT)

Time to first token (TTFT) measures the time from initiating a streaming request until the first generated text arrives.

A low TTFT can make an application feel more responsive because users begin seeing text sooner, even when the complete response takes longer to generate.

For example, if the first text arrives after 300 milliseconds and the response finishes after 4 seconds:

- TTFT is 300 milliseconds.
- Total latency is 4 seconds.

### Token Usage

Tokens are units of text processed by a language model. Token usage is commonly divided into input tokens and output tokens.

- **Input tokens:** Content sent to the model, including applicable instructions and conversation context.
- **Output tokens:** Content generated by the model, including any reasoning tokens accounted for in the API's output usage.

Tracking token usage helps developers understand consumption and estimate costs. Exact usage details depend on the API response and model.

### Errors

Error monitoring helps developers understand how frequently requests fail and why.

Useful measurements include total request count, failed request count, error rate, and error categories such as authentication failures, rate limits, timeouts, and interrupted streams.

The error rate can be calculated as:

**Error rate = (Failed requests / Total requests) × 100**

For example, if 5 out of 100 requests fail, the error rate is 5%.

### Cost

AI API costs depend on the model, applicable pricing, and usage. Developers can estimate request costs using the relevant input and output token counts and the model's current pricing.

Some models and APIs have additional pricing categories, such as cached input tokens. These should be included when applicable.

Cost monitoring can help identify unexpectedly expensive requests and opportunities to reduce unnecessary token usage.

### Using the Measurements Together

No single measurement explains every performance problem. For example, a high total latency with a low TTFT indicates that the delay may be occurring after the first text arrives. Further investigation is needed to determine the cause.

Tracking these measurements together helps developers investigate performance, reliability, usage, and cost.

## 3. Traces and Spans in an AI Request

### What Is a Trace?

A trace represents the journey of a single request through an application. It connects related operations so developers can investigate how a request was processed from beginning to end.

In an AI application, a trace might include preparing the input, calling an AI API, processing the response, and returning the result to the user.

### What Is a Span?

A span represents an individual operation within a trace. It can record information such as the operation's name, start time, duration, status, and relevant metadata.

A trace commonly contains multiple related spans. Spans can also have parent-child relationships when one operation calls or contains another operation.

### Example: Tracing an AI Request

Imagine an application that summarizes a document using an AI API.

A possible trace could contain these operations:

1. **Prepare input:** Validate the document and prepare the prompt.
2. **Call AI API:** Send the request and receive the response.
3. **Process response:** Extract or format the generated summary.
4. **Return result:** Deliver the summary to the user.

Each operation could be represented by a span if the application is instrumented to record it.

### How Traces and Spans Help with Troubleshooting

Suppose the complete request takes five seconds. A trace with useful timing data might show that most of the time was spent waiting for the AI API rather than preparing the input or processing the response.

Developers can use that evidence to narrow their investigation. They should still examine the underlying operation and supporting logs before concluding what caused the delay.

### Instrumentation and Context

Traces and spans do not automatically appear merely because an application calls an AI API. The application must use appropriate instrumentation or an integrated observability tool to create and record them.

For distributed applications, trace context can be propagated between services so related operations can be connected to the same trace. Instrumentation should preserve this context where supported.

### Important Limitation

The workflow above is illustrative. It describes how an AI request could be traced; it does not claim that the accompanying project currently implements tracing, span collection, or distributed trace-context propagation.

## 4. Troubleshooting Common Streaming Failures

### How Streaming Works

With a streaming AI API request, the application receives events as the response is generated. Instead of waiting for the complete response, the application can process text-delta events and display text incrementally.

Streaming improves perceived responsiveness, but it introduces additional failure scenarios that developers must handle.

### Failure 1: The First Text Arrives Slowly

**Possible symptoms:**

- The request starts, but no text appears for a long time.
- Users think the application is stuck.

**Investigation steps:**

1. Measure time to first token (TTFT).
2. Check request preparation time and network conditions.
3. Compare the behavior across representative requests.
4. Inspect available API timing information and error logs.

A high TTFT does not automatically identify the cause. Use the available evidence to determine which part of the request needs further investigation.

### Failure 2: The Stream Stops Unexpectedly

**Possible symptoms:**

- Some text appears, but the response never completes.
- The application stops receiving events.
- An error occurs while processing the stream.

**Investigation steps:**

1. Inspect the events received before the stream stopped.
2. Check for API errors, exceptions, timeouts, and connection interruptions.
3. Determine whether the stream ended normally or failed.
4. Check whether the application reports incomplete responses clearly.

Do not treat a stream that ends unexpectedly as a successful, complete response.

### Failure 3: The Response Is Empty or Incomplete

**Possible symptoms:**

- No text appears.
- The application returns only part of the expected answer.

**Investigation steps:**

1. Confirm that the request was sent with the expected input.
2. Check whether text-delta events were received.
3. Verify that the application handles the relevant event types and stream termination correctly.
4. Inspect errors and completion information provided by the API.

An empty or incomplete response can have several causes. Avoid assuming that every such case is an API failure; the application may also be handling events incorrectly.

### Failure 4: The Application Crashes During Streaming

**Possible symptoms:**

- An unhandled exception stops the application.
- The user sees a generic error or receives no useful explanation.

**Investigation steps:**

1. Inspect the exception and its stack trace.
2. Check error handling around asynchronous stream iteration.
3. Verify that resources are cleaned up appropriately when a stream fails.
4. Ensure that the application communicates failure without exposing secrets or sensitive data.

Error handling should preserve useful diagnostic information while presenting a safe, understandable message to the user.

### Recommended Troubleshooting Workflow

Use a consistent workflow when investigating a streaming failure:

1. Reproduce the issue with a controlled test.
2. Record the request's timing and relevant events.
3. Inspect errors and determine whether the stream completed normally.
4. Identify a likely cause using the available evidence.
5. Apply a focused fix.
6. Test both successful and failing cases again.

### Verification and Limitations

These troubleshooting steps describe recommended practices. Their presence in this guide does not mean that every diagnostic measurement or failure scenario is already instrumented or tested in the accompanying project.

Verify actual behavior with automated tests and, where appropriate, a controlled live API request. Keep credentials and sensitive request data out of logs.

## 5. Evaluating Answer Quality and Regressions

### What Is an AI Evaluation?

An AI evaluation is a systematic way to assess whether an AI application's outputs meet defined expectations.

Unlike a basic API test, which may check whether a request succeeds and returns a response, an AI evaluation also examines the quality of that response.

The appropriate evaluation criteria depend on the task. For a document summarization application, useful criteria may include correctness, relevance, faithfulness to the source, and adherence to the requested format.

### What Is a Quality Regression?

A quality regression occurs when a change causes an AI application to perform worse against one or more evaluation criteria.

Changes that may introduce regressions include:

- Modifying a prompt or system instruction.
- Switching to a different model.
- Changing retrieval logic or the context supplied to the model.
- Updating application code that processes model responses.

For example, shortening a summarization prompt might produce more concise summaries but also cause important facts to be omitted.

### Building an Evaluation Dataset

An evaluation dataset contains representative inputs and, where appropriate, reference answers, expected properties, or evaluation criteria.

A useful dataset should cover common use cases, important edge cases, and previously observed failures.

For a document summarization application, examples might include:

- A short document containing a few key facts.
- A long document with several important conclusions.
- A document containing ambiguous or conflicting information.
- An input that lacks enough information to support a reliable summary.

The dataset should reflect the application's intended use rather than only easy or ideal examples.

### Comparing Versions

To investigate the effect of a change, evaluate the old and new versions using the same representative dataset and consistent criteria.

A practical workflow is:

1. Run the evaluation dataset against the current version.
2. Record the results for the chosen quality criteria.
3. Make a prompt, model, or application change.
4. Run the same dataset against the updated version.
5. Compare the results and inspect examples where performance changed.
6. Investigate regressions before deciding whether to keep the change.

A change may improve one criterion while weakening another. For example, responses may become shorter but less complete. Evaluate the trade-offs against the application's requirements.

### Choosing Evaluation Methods

Different criteria require different evaluation methods.

- **Rule-based checks:** Verify properties such as required fields, valid JSON, or expected formatting.
- **Reference-based checks:** Compare outputs with trusted reference answers where suitable.
- **Human review:** Ask reviewers to assess qualities that require judgment, such as usefulness or factual accuracy.
- **Model-based evaluation:** Use a separate model to assess outputs against defined criteria, with appropriate validation and oversight.

Automated scores are not perfect measures of quality. Evaluation methods should be checked against realistic examples and human judgment where appropriate.

### Using Production Failures to Improve Evaluations

When a real failure reveals a gap in the evaluation dataset, consider adding a representative, privacy-safe example to the dataset.

This helps future evaluations check whether the same problem returns after a prompt, model, or application change.

Avoid copying sensitive production data into test datasets without appropriate authorization and safeguards.

### Verification and Limitations

Evaluation results provide evidence about performance on the examples and criteria being tested. They do not guarantee that every future response will be correct.

This guide describes recommended evaluation practices. It does not claim that the accompanying project already contains an evaluation dataset, automated quality scoring, or production evaluation pipeline.

## 6. Privacy, Sampling, and Retention

### Protecting Sensitive Data

AI observability data can contain sensitive information, including user prompts, model responses, personal details, and application metadata.

Before recording prompts, responses, or other request details, determine which information is necessary for debugging and monitoring.

Recommended practices include:

- Never log API keys, access tokens, passwords, or other secrets.
- Avoid collecting personal or confidential information unless it is necessary and appropriately authorized.
- Redact or remove sensitive fields before storing logs or traces.
- Restrict access to observability data according to team responsibilities.
- Review what third-party observability services collect and how they handle the data.

Removing secrets and unnecessary sensitive information reduces the risk of exposing private data during troubleshooting.

### Understanding Sampling

Sampling is the practice of recording only a subset of requests for observability.

For example, an application receiving thousands of requests might record a percentage of successful requests while retaining more detailed records for errors, where the instrumentation and configuration support that behavior.

Sampling can reduce storage requirements and observability costs. However, it can also make some issues harder to investigate because a request may not have been recorded.

When designing a sampling strategy, consider:

- The volume of requests.
- The importance of capturing failures.
- The level of detail needed for troubleshooting.
- The storage and cost implications.
- Whether the selected sample represents normal and unusual traffic.

Sampling rules should match the application's monitoring requirements rather than being chosen only to minimize cost.

### Defining Data Retention

Data retention describes how long logs, traces, evaluation results, and related records are stored.

A retention policy should consider:

- How long records remain useful for debugging.
- Privacy and security requirements.
- Applicable legal or organizational obligations.
- Storage costs and deletion procedures.
- Whether records need to be retained for audits or incident investigations.

Retaining data indefinitely is not automatically beneficial. Keep information only as long as there is a justified need and an appropriate basis for doing so.

### A Practical Privacy Review

Before using observability data to investigate an AI application, ask:

1. Does the record contain API keys, credentials, or other secrets?
2. Does it contain personal or confidential information?
3. Is every recorded field necessary for the intended purpose?
4. Who can access the records?
5. How long will the records be retained?
6. How can records be deleted when they are no longer needed?

These questions help teams balance useful debugging information with responsible data handling.

### Verification and Limitations

These recommendations describe general privacy, sampling, and retention practices. They do not establish that this project currently implements automatic redaction, request sampling, access controls, or data-retention enforcement.

Actual protections depend on the application's code, its logging and observability configuration, and any external services it uses. Verify those controls before claiming they are implemented.

## 7. Verification and Limitations

### What This Guide Covers

This guide explains practical concepts and troubleshooting approaches for AI API observability, including:

- Measuring latency, time to first token (TTFT), token usage, errors, and cost.
- Understanding traces and spans in an AI request.
- Investigating common streaming failures.
- Evaluating answer quality and identifying regressions.
- Considering privacy, sampling, and data retention.

The guide is intended to help developers reason about the behavior and reliability of AI-powered applications.

### What Has and Has Not Been Verified

The explanations and examples in this guide are educational documentation. They should not be interpreted as proof that every described capability is implemented in the accompanying project.

In particular, documenting a practice does not establish that the project currently has:

- A production observability backend or dashboard for durable metrics collection.
- Distributed tracing or automatic span creation.
- Automated AI quality evaluations.
- Automatic privacy redaction or sampling.
- Enforced data-retention policies.

Any claim that these capabilities are implemented should be supported by the relevant code, configuration, or test evidence.

### Current Project Instrumentation

The project reports metrics through a configurable callback that defaults to `console.log`.

The implemented metrics are:

- Operation name, duration in milliseconds, and success or error status.
- Input, output, and total token counts when usage information is available in the API response.
- Time to first non-empty text delta for streaming operations.
- Estimated request cost when the required token counts are available.

The greeting, summarization, and streaming metrics are covered by tests that use mocked SDK responses. These tests verify application behavior under simulated conditions; they do not prove live API performance or production telemetry.

#### Cost Estimation Limitations

The current cost estimator uses these standard GPT-5.5 text-token pricing assumptions:

- Input tokens: $5 per million tokens.
- Cached input tokens: $0.50 per million tokens.
- Output tokens: $30 per million tokens.

These rates are pricing assumptions configured in the code, not guaranteed invoice totals. The estimator does not account for every pricing adjustment or additional charge. For example, GPT-5.5 has higher rates for input contexts above 272K tokens, and eligible regional-processing endpoints have a pricing uplift.

The implementation is intended to demonstrate cost estimation from available token-usage data. It should not be treated as a complete billing calculator.

Verify current prices against the [official GPT-5.5 pricing documentation](https://developers.openai.com/api/docs/models/gpt-5.5) before relying on an estimate.

#### What Remains Unimplemented

The project does not yet export telemetry to a production observability backend or provide dashboards. Distributed tracing and automatic span creation remain future work.

Automated AI quality evaluation, automatic privacy redaction, configurable request sampling, and enforced data-retention policies are also not established as implemented capabilities.

### Verification Checklist

Before treating an observability feature as implemented, check the following:

1. **Code:** Is there code that performs the claimed behavior?
2. **Configuration:** Are the necessary settings present and correctly configured?
3. **Tests:** Is there evidence that the behavior works under the conditions being claimed?
4. **Documentation:** Do the instructions accurately describe the current implementation?
5. **Limitations:** Are untested scenarios and known gaps clearly stated?

For example, a unit test using a mocked API response can verify application behavior under simulated conditions. It does not, by itself, verify connectivity to the live API or prove that production observability is working.

### Keeping the Guide Accurate

As the project evolves, update this guide when implementation details, dependencies, or supported workflows change.

Prefer specific, verifiable statements over broad claims. If a feature is planned but not implemented, identify it as future work rather than presenting it as available.

The goal is to provide developers with documentation they can trust and use to make informed decisions.
